System Architecture

Problem Raw activity data without actionable training insight

Strava and Suunto produce rich streams of pace, heart rate, elevation and cadence — but their built-in analytics stop at charts and segments. Runners who actually want to train smarter (not just log miles) are left stitching together their own interpretations across multiple apps.

The result: most recreational runners either under-train, over-train, or plateau without knowing why. Generic feedback loops that just say "good job" or "slow down" don't move the needle.

Solution One analytics layer that turns streams into personalised insight

RunTrack normalises activity streams from Strava and Suunto into a single schema, then layers an LLM-driven analysis (Gemini Flash) over the data to produce per-run insight, weekly progress reports, PR detection and tailored training schedules.

The Next.js front-end focuses on map-heavy UX (Mapbox + Leaflet) and dashboards that answer questions runners actually ask — not just display numbers.

System Architecture

Problem Evaluating local LLMs against your own documents is manual and noisy

Open-source LLMs change every month. Picking the right one for retrieval-augmented generation over a private document set is guesswork: hosted evals are slow, expensive, and force your data through third-party infrastructure.

There's no easy way to compare models on the same retrieval task, on your own machine, with consistent chunking and embedding settings — which makes the chunking choices themselves hard to reason about.

Solution A local, reproducible RAG eval harness with pgvector at the core

A Python ingestion pipeline chunks documents (recursive splitter) and embeds them with Ollama-hosted nomic-embed-text. Embeddings land in pgvector for cosine/L2 retrieval, and a concurrent benchmark loop runs the same prompts against every local model in the pool, logging latency and token-rate metrics to JSONL.

A Next.js dashboard surfaces those metrics live — so model, chunking, and embedding choices become measurable instead of vibes.

System Architecture

Problem Read-heavy traffic saturates the relational database

A single PostgreSQL instance serving thousands of concurrent reads becomes the bottleneck — query latency climbs, connections pool out, and write traffic gets queued behind long-running reads.

Naively dropping Redis in front introduces a worse problem: stale data. Without atomic invalidation, the cache and database drift apart silently, and bugs only show up when a customer notices.

Solution Cache-Aside with atomic invalidation inside the DB transaction

An Express middleware intercepts every read: hit Redis first, fall back to Postgres on miss and populate the cache with a TTL. The write path wraps SQL updates and Redis evictions in the same database transaction so the cache cannot diverge from the source of truth.

k6 load matrices quantify the gain — thousands of virtual users with stable p95 latency — proving the cache pattern actually holds under contention.

# Distributed Cache-Aside System

PostgreSQL-backed store fronted by Redis with atomic invalidation.

## Stack

- Express (Node.js) for the API layer
- Redis 7 as the read-through cache
- PostgreSQL 16 as the system of record
- k6 for load testing

## Middleware sketch

    async function cacheAside(key, ttl, loader) {
      const hit = await redis.get(key);
      if (hit) return JSON.parse(hit);
      const fresh = await loader();
      await redis.set(key, JSON.stringify(fresh), "EX", ttl);
      return fresh;
    }

## Run

    docker compose up
    npm run dev
    k6 run tests/load.js
